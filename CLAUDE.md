# auth-server

Next.js 16 app in a pnpm + Turborepo monorepo, built on nuvui, shipped as a Docker image and a Helm chart. Conventions come from the `nuvraxis-frontend` plugin; its skills have the full rules.

## Ground rules

- **pnpm only.** Never write `npm`, `npx` or `yarn` in a file, script or command. Use `pnpm`, `pnpm dlx`, `pnpm exec`. Add dependencies to the workspace `catalog:` in `pnpm-workspace.yaml` and reference them as `"catalog:"`. One exception: `nextidp`'s README and the landing page tell its users `npm i nextidp`, since that's what they run.
- **Node 26**, the exact version in `.node-version`. The Dockerfile base and CI use the same version.
- **Biome formats and lints** everything except SCSS. Don't add ESLint or Prettier. A plugin hook runs `biome check --write` on each file Claude edits.
- **SCSS is BEM + nuvui tokens, linted by stylelint.** One block per file beside its component, global (not `.module.scss`), `@use` never `@import`, every color a token, no `!important`, never select a `nuv-` class.
- **This app uses nuvui. Read it before writing any UI** (see below). Change a component's look by prop → `--nuv-*` variable → token. Blocks: `pnpm dlx shadcn@latest add https://nuvui.nuvraxis.com/r/<name>.json`.
- **Server Components by default.** `"use client"` only on the leaf that needs state, effects or handlers.
- **Every Server Action and route handler** authenticates, validates input with valibot, and authorises against the resource itself.
- **Config:** `NEXT_PUBLIC_*` is baked in at build and identical in every environment. Everything per-environment is a runtime env var read on the server through `env()` in `src/shared/config/env.ts` (schema: `env-schema.ts`).

## Before writing any UI: read nuvui first

Never write nuvui code from memory. Before the first line of a page, component or stylesheet, read the library through the nuvui MCP (`.mcp.json`), passing the `@nuvui/react` version from `apps/auth-server/package.json` as `version`:

1. `get_rules`, then `get_rules` with each topic the work touches.
2. `get_changes` with the installed `@nuvui/*` versions.
3. `list_components` across every package, add-ons included.
4. `list_blocks`, and `list_charts` for any chart; `get_block` / `get_chart` for one that fits, and start from it.
5. `list_guides`, and `get_page` for each guide that applies.
6. `get_page` for every component you'll use, the whole page; `search_docs` for anything you can't place.
7. `get_tokens` before writing any CSS value.

If the MCP isn't connected, read the same from the `nuvraxis-frontend:nuvui` skill and say so.

Next.js 16 differs from older versions you may know: its own guides ship in `apps/auth-server/node_modules/next/dist/docs/`. Read the relevant one before using a Next API you're unsure of.

## Feature structure (apps/auth-server/src)

- `app/`: routing only. Thin `page.tsx` / `layout.tsx` / `route.ts` that import from features and shared; no business logic.
- `features/<feature>/`: `components/` (nuvui UI + BEM `.scss`), `actions/` (server actions: session, origin and valibot checks in each), `schemas/` (valibot), `server/` (server-only logic), `hooks/` (only if needed), `types.ts`, `index.ts` (the feature's public API).
- `shared/`: `config/` (env, app constants), `email/`, `ui/` (AuthCard, PageShell, TextLink, NonceProvider, `SessionList` (both session lists, from `toSessionRow`/`describeDevice` in `shared/auth/devices.ts`), `SectionBoundary` (Next's `catchError` with nuvui's `Alert` and Try again: an error boundary around one section of a page), `RowsSkeleton`/`TableSkeleton` in `list-skeleton` (loading placeholders shaped like an `Item` list or a table)), `styles/`, `auth/`, `appearance/` (light/dark and nuvui's presets: the root layout puts them on `<html>` from the `appearance` cookie; `AppearanceMenu` in the navbar and on the auth pages writes that cookie in the browser, not through a server action, which would re-render the page and lose what's typed). The auth pages' `AuthCard` shows `BrandMark` beside the name: the `LOGO_URL` image (optional; its origin is added to the CSP's `img-src` by `logoOrigin`) at 32 px, or the 24 px shield when it's unset or fails to load; `PageShell`'s top bar the same way at 28 px (shield 20 px). The tab's icon is `LOGO_URL` too, else the shield in `public/favicon.svg` (the root layout's `generateMetadata`). The product's name is `env().appName` (`APP_NAME`, default `DEFAULT_APP_NAME` "Auth Server"), read per request everywhere it's shown: page titles (the root layout's `generateMetadata`), the auth pages, `PageShell`, emails (each template takes `appName` and `logoUrl`), consent wording, the TOTP issuer, and the two-factor dialogs (passed down as a prop). `AuthCard` sits on `@nuvui/backgrounds`' `GradientBackground`, led by `--color-primary` so it follows the preset, with a pause button (WCAG 2.2.2).
- Boundaries, enforced by Biome (`noRestrictedImports` overrides in `biome.json`): other code imports a feature only as `@/features/<name>`; a feature never uses `../../` to leave its folder; `shared/` never imports from `features/`.

## Auth (apps/auth-server/src/shared/auth)

- `createAuth(deps)` in `auth-config.ts` is the whole Better Auth configuration, pure (env, database and email sender passed in). `getAuth()` in `auth.ts` builds it once, on first use: never at import, so `next build` needs no secrets. Route handlers that call it start with `await connection()` so they're never prerendered.
- Server code reads the session with `getSession()` / `requireSession(returnTo)` / `requireAdmin()` from `session.ts`. There is no browser auth client: every auth form posts to a server action, which runs the Better Auth endpoint through `callAuth` (`shared/auth/server-endpoint.ts` over the pure `callEndpoint` in `endpoint.ts`), i.e. `auth.handler(new Request(…))` with the browser's cookies, `X-Forwarded-For` and user agent, and copies the `Set-Cookie` headers into `cookies()`. Never `auth.api.*` for these: the server API skips the rate limiter and the hooks that read `oauth_query`.
- OIDC: the issuer is `BETTER_AUTH_URL` (bare origin). Discovery at `/.well-known/openid-configuration`, keys at `/jwks` (RS256), endpoints under `/api/auth/oauth2/*`. Code + PKCE (S256) and refresh for apps that sign people in; client credentials for services (within the client's `client_credentials_scopes`). No implicit, no device flow. Pushed authorization requests (RFC 9126, `shared/auth/pushed-authorization.ts`): `POST /api/auth/oauth2/par` (a form, rate limited like the token endpoint) authenticates the client through the plugin's own `getOAuthProviderApi(...).authenticateClient` (a secret for a confidential client, `client_id` alone for a public one), checks response type, registered redirect URI, PKCE S256 and scopes, and stores the parameters (no credentials) in `oauth_pushed_requests` (`@repo/db`, not a Better Auth table) under the SHA-256 of a 60-second `request_uri`; the plugin's `requestUriResolver` (`pushedRequestResolver`) hands them back once, to that client only (`consumePushedRequest` deletes as it reads). Discovery advertises `pushed_authorization_request_endpoint` through `extendOAuthProvider`; `require_pushed_authorization_requests` is false (no client is made to use it), and `request_uri_parameter_supported` stays the plugin's false (that one is about request objects). Each parameter once: a pushed request can't carry two `resource`s.
- Signed-in pages live under `app/(app)/`: the layout renders `PageShell` and checks the session, and every page and server action checks again itself (`requireSession(path)` / `requireAdmin(path)`), because layouts don't re-run on every navigation. Each page renders its own `PageHeader`. Routes that read the session set `export const instant = false`: they block on the session check by design.
- `proxy.ts` sends `/account/*` and `/admin/*` without a session cookie to `/login?returnTo=…` (convenience only), sets the nonce CSP (`shared/security/csp.ts`) on every document, and passes `x-pathname` for layouts. When the browser sends one of our cookie names twice (a copy from another cookie scope: a deployment on a parent domain, or this server before `COOKIE_DOMAIN` changed), and on every form post, it also expires the copies this server doesn't write (`strayAuthCookieDeletions` in `shared/auth/stray-cookies.ts`), as raw `Set-Cookie` headers so the page's own `cookies()` keeps the session: Better Auth reads the first of two and Next's `cookies()` the last, so `/login` and the authorize endpoint would disagree about the session and loop. Every `returnTo` goes through `safeReturnPath`.
- Auth forms: a server action in `features/<f>/actions/` (valibot via `parseForm` on the server, then a function in `server/` that takes an `AuthCaller` and returns an outcome, so tests drive it with the harness browser's `caller()`), and a thin client form: `useActionState` + `AuthForm` (Next's `<Form>` from `next/form`) + `SubmitButton`, fields in nuvui `Field`s with `defaultValue`s from the state, keyed by `state.attempt`, focus on the first invalid field. Errors through `authErrorMessage` (never the server's text). Same answer whether or not an email exists. The forms work with JavaScript off (the page re-renders with the action's state).
- Where an auth step leads: a page of this server is a server `redirect()` (`continueTo`, `redirectToSafePath`); an app's redirect URI (another site) is returned as `{ status: "leaving", url }` and rendered by `LeavingFor` (navigates with JavaScript, a Continue link without), because `form-action 'self'` blocks a cross-site redirect after a form POST. Destinations posted in hidden fields (`next`, `returnTo`, `oidcQuery`) go through `safeReturnPath` / `signedOidcQuery` again on the server.
- Links between auth pages: `authPageHref(page, query)` (shared/auth/auth-pages.ts). In an OIDC flow, pass `signedOidcQuery(searchParams)` along unchanged; to resume after an email round trip, use `authorizeUrlFrom(...)` (a fresh authorize request) as the destination, with `{ freshSignIn: true }` when the emailed link itself signs the user in (confirmation, magic link) so `prompt=login`/`max_age` don't send them back to /login. Redirect to query-string paths only through `redirectToSafePath`.
- Emails (`shared/email`): React Email components in `emails/` (one per email, a default export with `PreviewProps` for `pnpm email:dev`), built from `components/email-layout.tsx` (`EmailLayout`, `EmailText`, `EmailAction`, `EmailNote`): inline styles in hex (nuvui's light palette; mail apps ignore stylesheets and CSS variables), the `LOGO_URL` image beside the name unless it's an SVG. `templates.tsx` renders each to HTML with `render` and makes the plain-text part from that HTML with `toPlainText` (`data-skip-in-text` leaves out the header and the copy-this-address line; every link stands alone between spaces, which the E2E mailbox and `linkIn` rely on). Rendering is async, and it must not delay the response (timing would reveal which addresses have accounts), so `createAuth`'s `sendEmail(to, promise)` takes the template's promise unawaited: `sendEmailInBackground` renders and sends after the response; the test harness waits for it at the end of each request.
- Two-factor: `/two-factor` keeps the query `/login` handed over (so verifying resumes an OIDC flow); turning it on, new backup codes and turning it off are `TwoFactorSettings` from `@/features/two-factor`, each behind the password. TOTP tests compute codes with an independent RFC 6238 implementation, as authenticator apps do.
- Consent: `/consent` shows only what the signed query vouches for (`verifyOAuthQueryParams` with `BETTER_AUTH_SECRET`, in `readConsentRequest`); an altered or expired query offers "start again", no session starts the request again through sign-in. Allow/Deny post to `consentAction` (`/oauth2/consent` with the signed query), which Better Auth re-checks before answering with the way back to the app; "Use another account" signs out and restarts the request.
- OIDC clients (`/admin/clients`): server actions in `features/oidc-clients/actions/`, because `adminCreateOAuthClient` is server-only. Each action runs `requireAdmin`, valibot, then a function in `server/clients.ts` that calls the plugin with the request headers (the plugin checks the admin again). Every client gets code + refresh grants and `require_pkce`; public ones have no secret. Secrets are stored hashed and shown once. `clientReference` makes the admins as a group the owner (`ADMIN_CLIENT_OWNER`), so any admin can edit, rotate or delete any client. Editing changes the name and redirect URIs only (`adminUpdateOAuthClient`, which checks the URIs as on create); a client's kind stays, as changing it would add or drop its secret. A client the plugin says isn't the admins' is `not-allowed`. The list is ten a page, newest first (`?page=`, `CLIENTS_PER_PAGE`; `countOAuthClients` and `listOAuthClients` from `@repo/db`), with nuvui's `Pagination` as links (`ListPagination` in `shared/ui`, `PageNumberSchema` and `pageWindow` in `shared/validation/paging.ts`, shared with the session list); a page past the end redirects to the last one, as after deleting its only client.
- Users (`/admin/users`, `features/user-admin`): Better Auth's `admin` plugin underneath, without impersonation, setting passwords or emails, or creating users (`DISABLED_ADMIN_PATHS` in `auth-config.ts`). The list is ten a page with `?q=` (name or email) and `?status=` as a GET form (`listUsers`/`countUsers` from `@repo/db`); `/admin/users/[id]` disables (`ban-user`, with a reason for admins only and an optional end) and enables, signs out everywhere (`revoke-user-sessions`), requires two-factor or stops requiring it and resets it (`setTwoFactorRequired`/`resetTwoFactor` from `@repo/db`: the plugin has no endpoint for those), changes the role, and deletes once the email is typed. The page: a nuvui `Breadcrumb`, the header card, then its sections: where they're signed in (ten a page, `?page=`, read-only but for Sign out everywhere), Manage the account (`Item` rows), the danger zone, and the history beside them from `lg`. The header waits for the account; the sessions and the history stream in, each in its own `Suspense` (with a skeleton from `user-skeletons`) and `SectionBoundary`. The route has `loading.tsx` (`UserScreenSkeleton`), `error.tsx` and `not-found.tsx` (a deleted account's old link), and the list its own `loading.tsx` in a `(list)` route group, so it doesn't wrap `[id]` (a direct load of a user's page would show the list's skeleton). `/admin/clients` has a `loading.tsx` too (`ClientsScreenSkeleton`), and My profile's Sessions page streams its list behind a skeleton, under the profile and tabs that show at once. Each action: `requireAdmin`, valibot, then a function in `server/manage.ts` that takes an `AdminDeps` (caller, db, actor, `sendEmail`, env; tests pass the harness's) and finds the account again, refuses the admin's own (`self`), calls the endpoint through `callAuth`, writes an `admin_actions` row (`@repo/db`: action, target id, actor user or client id, a fixed `detail`; no emails or reasons, no foreign key to the target, so it outlives the account) and emails the person (disabled, enabled, two-factor reset, deleted). `account-policy.ts` holds the rules on the public endpoints: roles are `user`/`admin` only and never your own; ending someone's sessions also revokes every OAuth token they hold (`revokeUserOAuthTokens`), because the OAuth plugin keeps `offline_access` refresh tokens past a session; nobody who must have two-factor can turn it off. A disabled account's sign-in (`BANNED_USER`, refused only after the password or code was right) says so through `DISABLED_ACCOUNT_TEXT`. The machine API for other services is planned, not built (the logic is already caller-agnostic).
- Required two-factor (`shared/auth/two-factor-policy.ts`): `twoFactorRequired` on the user (set by an admin), or every admin when `TWO_FACTOR_REQUIRED_FOR_ADMINS=true`. Until it's on: `requireSession` sends them to `/account/security/two-factor` from every page but it and the password page; the OAuth plugin's `postLogin` sends an app's sign-in there with the signed query, before consent or a code, and `ContinueSignIn` (`/oauth2/continue` with `postLogin: true`, asked again by the plugin; a fresh authorize request if the query expired) goes on once it's on; `/api/auth/get-session` over HTTP answers `null`, so shared-cookie apps see no session (this server's own pages read it through the server API).
- Cloudflare Turnstile (`shared/auth/captcha.ts`), only when `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are both set (one alone fails `env()`). Better Auth's `captcha` plugin checks the token on every endpoint in `CAPTCHA_ENDPOINTS`, so the public `/api/auth/*` is guarded, not only the forms; it checks the token's hostname in production only (Cloudflare's test keys report example.com). Every form that posts typed input renders `<Turnstile />` (`shared/ui/turnstile`; nothing without a site key) inside its `<form>`, and its action calls `withCaptcha(callAuth, captchaToken(form))`. A new form that posts to one of those endpoints needs both, and a new endpoint behind a typed form goes in `CAPTCHA_ENDPOINTS`. The admin's "New client" posts to the plugin's server API, and the Users screens' typed forms (disable, delete) to admin endpoints, neither of which the captcha plugin guards, so their actions call `formPassesTurnstile` (`shared/security/turnstile-form.ts`) themselves. Refusals read "Complete the security check" through `authErrorMessage`. The CSP adds Cloudflare's script and `frame-src` only when it's on. Turnstile needs JavaScript: with it on, the forms don't work with JavaScript off.
- Social sign-in (`features/social-sign-in`, `shared/auth/social-providers.ts`): Google, Microsoft, GitHub, and one generic OpenID Connect provider (`SSO_*`, Better Auth's `genericOAuth`, provider id `sso`), each on when its client ID and secret are both set (half fails `env()`). The login and sign-up pages put `SocialSignIn` above their form, from `socialSignInPageContext`, which also takes Better Auth's `?error=` off the query (the signed OIDC query wouldn't verify with it) and explains only known codes, never `error_description`. The button's action calls `/sign-in/social` through `callAuth` with the signed query as `oauth_query`: the oauthProvider plugin then continues the app's flow after the callback. Better Auth's account-linking defaults stay (both emails verified, no trusted providers); every provider has `requireEmailVerification`; provider tokens are stored encrypted. Microsoft (nOAuth): `microsoftEmailVerified` replaces Better Auth's reading of "verified", which another tenant's admin controls: only `xms_edov`, personal accounts, or the one tenant `MICROSOFT_TENANT_ID` names. Two-factor: Better Auth asks for it only after a password, so `socialTwoFactorGuard` (before `oauthProvider` in the plugins) refuses a provider sign-in for an account with two-factor on and sends it to `/login?error=two_factor_required`. A password-less account sets a password through the reset email (Better Auth creates the credential account); the account page says so. Tests: `shared/auth/social-sign-in.test.ts` plays an identity provider behind a stubbed fetch.
- Account security, "My profile" in the navbar: three pages behind vertical tabs (`SecurityLayout`: `ProfileHeader` (avatar with the picture or initials, the name as the h1 with an Admin badge, "Signed in as …", and member since, two-factor and how they sign in), then nuvui's `NavigationMenu` named "Profile settings" with `orientation="vertical"` and `next/link`s marked `active`, a row on a phone; links, not `Tabs`, because each is a page), at the paths in `SECURITY_PAGES` (`shared/auth/account-pages.ts`): `/account/security` (`SecurityPasswordScreen`: the password and linked accounts; where sign-in lands), `/account/security/two-factor` (`SecurityTwoFactorScreen`, the two-factor card passed in by the page) and `/account/security/sessions` (`SecuritySessionsScreen`). Each page and action checks the session with its own page as the way back. Changing the password is `changePasswordAction` (`/change-password` through `callAuth`: rate limited, signs out other devices, this browser gets a new session cookie). Sessions are listed from `@repo/db`, ten a page with this browser's first (`listActiveSessions` with `first`, `countActiveSessions`; no tokens; Better Auth's list-sessions refuses sessions older than a day), with `?page=` and `ListPagination` like the client list, and revoked through server actions that look up the token server-side (`getSessionToken`, scoped to the user) and call Better Auth. "Sign out everywhere" is `revokeSessions`, then `/login`.
- APIs (`OAUTH_RESOURCES`, `OAUTH_API_SCOPES`, both optional): the oauthProvider plugin's RFC 8707 resources, seeded on start (insert only; a removed URI stays in `oauth_resources`). A token asked for with `resource` is an RS256 JWT with that `aud`; without it, an opaque token (userinfo, introspection). `enforcePerClientResources` is on: a client gets tokens only for resources it's linked to (`oauth_client_resources`), else `invalid_target`. API scopes are offered beside the OIDC ones (`offeredScopes`) and described on the consent screen (`consentScopes`). `skip_consent` is for first-party clients only. RP-initiated logout is the plugin's `/oauth2/end-session`: `oidcClientDefaults()` turns on `enable_end_session` for every client that signs people in (admin screen, seed, provisioning), which also puts `sid` in their ID tokens; without it the plugin refuses the client. With a valid `id_token_hint` for this browser's session it ends the session and redirects to a registered `post_logout_redirect_uri` only (exact match, with `state`); otherwise it shows its own plain confirm or "Logged out" page. Post-logout URIs come from provisioning and the seed; the admin screen doesn't set them. Tests: the "RP-initiated logout" describe of `auth-config.test.ts`. Back-channel logout is the plugin's: when a session is deleted (sign-out, revocation), each client with a `backchannel_logout_uri` (https or loopback, the plugin refuses http) that holds a stored token for that session (a refresh token, i.e. `offline_access`) gets a signed logout token. Clients for a deployment come from `pnpm clients:provision <file>` (`apps/auth-server/scripts/provision-core.ts`, example in `scripts/clients.example.json`): types `web` and `machine`, found again by name and updated, never duplicated or deleted, but only clients it created (`metadata.provisioned_by`), and it checks the whole file first and refuses dropping a post-logout or back-channel URI (the plugin can't clear them); it mints a five-minute session for `PROVISION_ADMIN_EMAIL` (an admin) instead of signing in, so two-factor admins work, and refuses scopes and resources the server doesn't offer. Tests: the last describe of `auth-config.test.ts`, and `scripts/provision.test.ts`.
- Example client (`apps/example-client`, `http://app.localtest.me:3001`, `EXAMPLE_*` env): the shared-cookie card forwards only `nvx-auth.*` cookies to `/api/auth/get-session`; the OIDC flow is `nextidp` (`features/oidc/server/auth.ts`: `idp()` from `nextidp/next` with `basePath: "/oidc"`, the redirect URI the seed registers; `app/oidc/[...nextidp]/route.ts`; `proxy.ts` runs `auth.proxy()` before its CSP). `auth.ts` reads the settings through `parseEnv`, not `env()`, because the proxy imports it and `server-only` throws there. Sign-out has two buttons on one form: "Sign out of this app" (revoke and clear its cookie; the auth server's session stays, so the next sign-in goes straight through) and "Sign out of the auth server too", (a `signOutOfIdp=true` button), which then redirects to `end_session_endpoint` with the kept ID token as `id_token_hint` and the home page as `post_logout_redirect_uri` (the seed registers it, and adds it to an example client seeded before); its CSP's `form-action` names the auth server's origin, because form-action covers that redirect. Its POST routes check `Origin`. It talks to the auth server only through public endpoints, never `@repo/db`. Its `dev` script builds `nextidp` first (pnpm runs no `predev`), so the E2E suite gets a fresh build.
- `nextidp` (`packages/nextidp`), published to npm, ES module and CommonJS from one source: `scripts/build.ts` compiles each file with esbuild into `dist/esm` and `dist/cjs` (not bundled, so the entry points share one core), each folder with its own `package.json` type and a copy of tsc's declarations. Relative imports end in `.js` (a Biome override enforces it), because the ES build runs in plain Node. The core (`nextidp`) is Web `Request`/`Response` only: `createIdp` in `src/idp.ts` (exported as `idp`) checks its settings on first use (`resolveConfig`; options, else `IDP_*`; one `misconfigured` error naming everything wrong), and keeps its caches per instance, never in module scope. Cookies are A256GCM JWTs with an HKDF key per purpose (`Sealer`, secret rotation), `__Host-` names on https, split past 3800 characters (`cookies.ts`). Refresh shares one request per refresh token for 30 s (the server rotates them), and only a 400/401 ends the session. `nextidp/next` adds `routes()`, `proxy()`, `session()`, `requireSession()` and `withToken()` (a route handler of an API). APIs: `verifyAccessToken`/`verifyBearer` in the core (`src/access-token.ts`) check a JWT access token against the JWKS (`typ` at+jwt required, `iss`, `aud` = `audience`, expiry, 60 s skew), an opaque one by introspection with the API's own client credentials (the auth server answers only for tokens that client was issued, or for an API it's linked to; the token must name `audience` too, unless `acceptOwnTokens`; kept a minute at most), then the scopes; refusals are 401/403 with RFC 6750's challenge (`tokenRefusal`), and a token that can't be checked is 503, never a pass. `http.ts` rethrows a failed request as a bare `Error` with its message only (the HTTP client's errors can carry the request, the introspection secret included), and the adapters log error codes, never errors. An API's settings are only `issuer` and `audience` (`resolveApiConfig`; sign-in's `appUrl` and `secret` aren't needed; `audience` is never taken from `resource`, the API an app asks tokens for, or an app would accept tokens meant for that API), and `resource`/`audience` are kept exactly as written, because the auth server compares them as strings. `nextidp/express`: sign-in through `express()` (nextidp's routes, then the session read and refreshed for `sessionOf(req)`), `requireSession()` (a signed-out GET goes to sign in, anything else 401), and for APIs `requireToken()` and `tokenOf(req)`; all of it Node `IncomingMessage`/`ServerResponse` middleware. `nextidp/node`: `handle(req, res)`, `session(req, res)`, `requireSession(req, res)` for Node's own server. Both go through `node-adapter.ts` over `node-http.ts`, which turns a Node request into a Web `Request` on `appUrl`'s origin (never the Host header), takes a form a body parser already read from `req.body` or reads it (64 KB at most, else 413), and refreshes only while the response's headers are unsent (a rotated refresh token must reach the browser); the session is read once per request (a `WeakMap`). Tested with a real Express 5 app and a `node:http` server (`src/node.test.ts`). Service tokens (`src/service.ts`): `serviceToken({ scopes, resource })` in the core asks the token endpoint with client credentials (`resolveServiceConfig`: issuer, `clientId` and `clientSecret` required, `resource` defaulting to IDP_RESOURCE), keeps each token per scopes and API until a minute before it expires (half its life if shorter; not at all without `expires_in`), shares one request between concurrent calls, and never keeps a refusal (`service_token_failed`). `dropServiceToken(token)` forgets one; `useServiceToken(client)` adds a request interceptor that puts the token (replacing any Authorization, whatever its case) only on requests to the allowed origins (`origins`, else the origin of an http(s) `resource`; neither refuses to start; the origin is `new URL(url, baseUrl)`'s, so an absolute or protocol-relative URL elsewhere gets no token), and a response interceptor that, on a 401 from those origins, drops the token and replays once with `retried: true`; tokens are kept under `JSON.stringify([resource, scope])` and a resource with whitespace is refused, to a fast-http-client client typed structurally (`InterceptableClient`), so another version of it fits. NestJS injects `IDP` for it. Sessions in a store (`src/store.ts`): without `store` a session is its sealed cookie (`cookieBackend`); with one (`SessionStore`: `get`/`set`/`delete` over strings, TTL in seconds; `memoryStore()` for one process) the cookie holds a sealed `{ id }` (purpose `nextidp:session-reference`) and the store a sealed session plus `createdAt` (`nextidp:stored-session`), under keys prefixed `nextidp:<clientId>:` so apps sharing a store stay apart (`storeBackend`). The core reaches sessions only through the backend's `load`/`create` (a sign-in; removes the browser's previous stored session)/`update` (a refresh)/`remove`. `POST <basePath>/backchannel-logout` exists only with a store: `verifyLogoutToken` (`src/logout-token.ts`; OIDC Back-Channel Logout 1.0, 2.6: signature by the JWKS, `iss`, `aud` = clientId, `iat`, `exp`, the logout event, `sid` or `sub`, no `nonce`, `typ` logout+jwt when present), then a mark under `ended-sid:<sid>`, or, for a token with no `sid`, `ended-sub:<sub>` with the time; `load` checks both (the ID token's `sid` claim, and `createdAt` against the sub mark) and deletes an ended session. 400 for a bad token, 500 if the store fails. The plugin sends a logout token with `typ` logout+jwt, `iss` = `BETTER_AUTH_URL` (the jwt plugin's issuer), `aud` = client ID, `sid` (the Better Auth session id, the same as the ID token's) and `sub`, only to clients holding a stored token for that session. A refresh refused with 400/401 checks the store again first (`refreshedElsewhere`): another instance may have rotated the token. `nextidp/nestjs`: `IdpModule.forRoot()`/`forRootAsync()` (a global `APP_GUARD` unless `protectAll: false`), `IdpGuard`, `@Scopes()` (controller's then route's, all needed), `@Public()`, `@CurrentToken()`; written without decorator syntax (decorators applied as calls, explicit `Inject` tokens), so esbuild builds it and Nest 11 (CommonJS) and 12 (ES modules) both load it; tested with a real Nest 12 app. Node ≥ 24. HTTP goes through `fast-http-client` (no circuit breaker, no retries on posts). Its own dependencies are ranges, from the named catalog `catalog:nextidp`. Tests: `src/*.test.ts` against a fake provider (`test/fake-issuer.ts`, a stubbed fetch); `pnpm --filter nextidp check:package` runs publint and Are the Types Wrong on the packed tarball (PRs run it too). Releases: bump its `version` and `CHANGELOG.md`, merge, tag `nextidp-vX.Y.Z`. The planned scope shipped as 0.1.2 (`plan_idp_sdk.md`; further ideas are issues #49 to #53). Changes since a release go under a "## Unreleased" heading in its changelog until the next one.
- Telemetry (`shared/telemetry/`, `src/instrumentation.ts`): OpenTelemetry through `@vercel/otel`, exported only when `OTEL_EXPORTER_OTLP_ENDPOINT` (or the metrics one) is set; those standard `OTEL_*` variables are read from `process.env` (`metricsExportEnabled`), not `env()`, because `register()` runs before `env()` can. Next and Better Auth trace requests, endpoints, hooks and queries themselves. Each server action wraps its feature's server call in `traceFlow("<flow>", …)` (the flows are the `AuthFlow` union): a span named after the flow with `auth.outcome` read from the result (`outcomeOf`: its `kind`, a problem's name, `ok`/`failed`), and the `auth.flow.duration` histogram by flow and outcome; `callAuth` adds Better Auth's error code to that span. A new action that signs in, changes credentials or changes a client gets a flow. Span attributes are fixed words and ids only: never an email, name, password, code, token or error message. Web vitals: the root layout renders `WebVitalsReporter` only when metrics are exported; it posts LCP, INP, CLS, FCP and TTFB to `/api/vitals` when the page is hidden, which accepts this origin only, a small body and known values, maps paths to `KNOWN_ROUTES` (a test keeps that list equal to the pages in `src/app`), and records `browser.web_vital.*` histograms.
- `auth-config.test.ts` drives the real configuration over HTTP against PGlite (`@repo/db/testing`). Change the config, change or extend those tests.

## Delivery

PR → `pr.yaml` checks (Biome, stylelint, typecheck, build, Docker build + health check, helm lint + kubeconform). Nothing is published. A first `changes` job sorts the diff, so each part is checked only when it changed: `quality` and `build` for any code (both `turbo --affected`, so a nextidp change never tests or builds the auth server, nor the other way round), `docker`, `helm`, `db` and the seed build for what goes into the auth server's image (the same list as `main.yaml`'s `paths-ignore`), and `nextidp` (build, publint, Are the Types Wrong) for the package or the root config it builds on. A skipped job counts as passed for required checks.
Merge to `main` → `main.yaml` builds the image once (amd64 + arm64) and pushes `ghcr.io/sajanv88/auth-server:sha-<short-sha>` and `:main`, unless the push changed only what isn't in the image (its `paths-ignore`: `apps/landing`, `apps/example-client`, `apps/tests`, `packages/nextidp`, `pages.yaml`, `e2e.yaml`, `nextidp-release.yaml`, Markdown); `workflow_dispatch` builds main's head by hand.
Tag `vX.Y.Z` → `release.yaml` retags that commit's image as `:vX.Y.Z` and `:latest` (no rebuild; for a commit `main.yaml` skipped, the nearest earlier image on main, and only if nothing in the image changed since: `in_image()` mirrors the `paths-ignore`), pushes the chart to `oci://ghcr.io/sajanv88/charts/auth-server` at `X.Y.Z`, and creates the GitHub Release.
Tag `nextidp-vX.Y.Z` → `nextidp-release.yaml` checks the tag against `packages/nextidp/package.json` and main, tests, builds and checks the package, publishes it to npm with trusted publishing (OIDC, no npm token; the job runs in the `npm` environment, whose reviewers approve it), and creates a GitHub Release from its changelog.
Argo CD syncs the chart from the OCI registry (production) or from `charts/auth-server` in git.

Deploying: the chart's ConfigMap carries every non-secret setting the app validates at startup (`BETTER_AUTH_URL`, `COOKIE_DOMAIN`, `TRUSTED_ORIGINS`, `TRUSTED_PROXIES` = the ingress pods, `EMAIL_*`, `SMTP_HOST/PORT/USER`, `TURNSTILE_SITE_KEY`, the sign-in providers' client IDs, `MICROSOFT_TENANT_ID`, `SSO_NAME`, `SSO_DISCOVERY_URL`, `OAUTH_RESOURCES`, `OAUTH_API_SCOPES`, `TWO_FACTOR_REQUIRED_FOR_ADMINS`, `APP_NAME`, `LOGO_URL`, and `OTEL_*`); one existing Secret named by `existingSecret` holds `BETTER_AUTH_SECRET`, `DATABASE_URL` and `SMTP_PASSWORD`, plus `TURNSTILE_SECRET_KEY` when Turnstile is on and each configured provider's `*_CLIENT_SECRET` (the chart never creates it; rendering fails without the name). The migrate Job reads only `DATABASE_URL` from it.

Release ritual: merge to main → wait for `main.yaml` to go green (a merge it skipped can be tagged at once) → `git tag vX.Y.Z && git push origin vX.Y.Z`. Never edit `version`/`appVersion` in `Chart.yaml`; the release sets them.

## Database (nuvraxis-fullstack)

PostgreSQL through Drizzle ORM v1, in `packages/db` (`@repo/db`). Rules: the `nuvraxis-fullstack` skills `drizzle-postgres`, `db-package` and `postgres-ops`; drizzle-kit itself: the vendored `drizzle-kit*` skills.

- `packages/db` is the only package that imports `drizzle-orm` or `pg`. Apps import `db`, types and query functions from `@repo/db`.
- Schema change: edit `packages/db/src/schema/`, then `pnpm db:generate`, read the SQL, commit it. Never edit a committed migration; add a new one. Never `drizzle-kit push` outside a throwaway local database.
- Validate input with valibot before any insert; never pass `FormData` to a query.
- Better Auth reaches the database only through `createAuthAdapter(db)` from `@repo/db`, and must run with `advanced.database.generateId: "uuid"` (the adapter refuses to start otherwise). The tables mirror Better Auth's `getAuthTables()` for our plugin set: adding or upgrading a Better Auth plugin means a schema change, a migration, and an updated `src/auth-adapter.test.ts`, which runs a real `betterAuth()` against the migrated schema.
- The admin plugin's columns: `users.banned`, `ban_reason`, `ban_expires` (a disabled account), `sessions.impersonated_by` (always null: impersonation is off), beside our `users.two_factor_required` and the `admin_actions` audit table. A disabled account whose end has passed counts as active (`userStatus`); Better Auth clears it at the next sign-in.
- `@better-auth/oauth-provider` needs `clientPrivileges` (admins only) to create clients, `clientReference` so admins share them, and `allowInsecureRedirectUri` to accept `http://` redirect URIs at all: the plugin refuses `http` for web clients even on loopback. Ours (`allowInsecureRedirectUri` in `auth-config.ts`) allows `localhost`, `127.0.0.1`, `[::1]` and `*.localtest.me` in development, nothing in production. Every refusal is logged by `server/clients.ts`, and the admin's forms say what to do: the redirect-URI hint for this environment, "sign in again" for a lost admin session, "the reason is in the log" for anything else.
- Local database: `cp .env.example .env`, point `DATABASE_URL` at a Postgres database (or `docker compose up -d`), then `pnpm db:migrate`, and `pnpm db:seed` (needs `SEED_ADMIN_PASSWORD`) for an admin and the example client's registration. The seed (`apps/auth-server/scripts/seed.ts`, bundled by esbuild) goes through Better Auth like the app, sets only the admin role and confirmed email directly, is safe to run twice, and refuses `NODE_ENV=production`.
- Never commit `.env` or any `DATABASE_URL` with real credentials. In Kubernetes it comes from an existing Secret, and the chart only references it by name.
- Migrations reach production as an Argo CD PreSync Job running `node packages/db/dist/migrate.mjs` from the app image.
- The drizzle-kit MCP server is in `.mcp.json` but disabled in `.claude/settings.json`: it can `push` and `pull` against whatever `DATABASE_URL` is set. Enable it only while that points at a local database.

```sh
pnpm db:generate   # new migration from the schema diff
pnpm db:check      # migration conflicts across branches
pnpm db:migrate    # build + apply with the bundled runner
pnpm db:seed       # local admin + the example client (SEED_ADMIN_PASSWORD in .env)
pnpm clients:provision <file>   # the clients a file declares (PROVISION_ADMIN_EMAIL), any environment
pnpm db:studio     # local inspection only
```
